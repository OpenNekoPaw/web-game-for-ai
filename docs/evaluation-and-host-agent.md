# 模型、推理强度、策略评估与主持 Agent

本文定义后续评测与比赛编排的目标边界。当前版本只保存设计，不把主观评估逻辑放进游戏裁判。

## 设计原则

- 游戏服务是确定性裁判，负责发牌、动作合法性、回合推进、超时、计分、结算和可审计回放。
- 胜负与标准统计由服务端计算；模型判断只用于赛后质量分析，不得改写合法动作或比赛结果。
- 模型、推理强度和策略是三个独立变量。正式实验一次只改变一个变量，其他条件保持一致。
- 单局结果受发牌和座位影响，不能用于模型排名。评估至少使用多局比赛，并优先采用同牌复战和地主席轮换。
- Agent 自报的模型与推理强度属于声明信息。可信排行榜需要平台注入的运行配置、调用日志或签名证明。

## 评估职责

### 服务端裁判

服务端直接生成无需模型判断的指标：

- 胜负、零和得分、地主/农民身份、倍率及倍率来源。
- 接受动作、拒绝动作、非法动作、超时、出牌和不要次数。
- 每次决策耗时、总出牌张数、最终剩余张数。
- 炸弹、火箭、春天、反春以及公开动作时间线。
- Agent、模型声明、推理强度、客户端版本、策略 ID/版本/hash 和座位信息。

这些数据构成排行榜和复现实验的事实层。

### 评估 Agent

评估 Agent 读取完整公开回放、各席位自己的复盘以及服务端指标，输出结构化分析：

- 关键叫牌、拦截、让牌、拆牌和收尾决策的质量。
- 是否存在无效顶队友、过早消耗控制牌、遗漏直接获胜或阻断路线。
- 问题属于偶发执行错误、策略规则缺陷，还是模型在相同策略下的推理失败。
- 建议修改的策略规则及其回放证据。

评估 Agent 不读取比赛中不可公开给目标席位的隐藏信息来判定“当时是否合理”。如需使用全牌面做反事实分析，报告必须明确标记为赛后全信息分析，不能冒充该席位当时可知的信息。

### 排名聚合器

排名聚合器应是普通程序，不需要大模型。建议分别计算：

- 总得分、胜率、地主胜率、农民胜率和座位分布。
- 同牌同席差分：候选配置相对基线配置的平均得分变化。
- 非法动作率、超时率和决策耗时分位数。
- 评估 Agent 给出的错误类别计数，但不把单次主观评分直接混入官方得分。

## 实验矩阵

每条参赛配置使用不可变快照：

```json
{
  "modelId": "gpt-5.6",
  "reasoningEffort": "high",
  "strategyId": "default",
  "strategyHash": "sha256:...",
  "clientVersion": "arena-client-0.3.0"
}
```

推荐三类实验：

1. 模型评估：固定推理强度、策略和客户端，只替换模型。
2. 推理强度评估：固定模型、策略和客户端，只替换推理强度，同时比较质量、耗时和超时率。
3. 策略评估：固定模型、推理强度和客户端，只替换策略 hash。

每组候选与基线应使用相同初始牌局，并让候选轮换 A/B/C 三个座位。样本量不足时只展示实验结果，不生成稳定排名。

## 主持 Agent

主持职责与裁判职责必须分离。主持 Agent 或主持程序负责：

- 创建比赛并选择 `invite_only` 或 `private` 接入策略。
- 为每个座位生成邀请、核对 Agent 声明信息和策略快照。
- 等待三席准备，启动和监控每轮，处理浏览器刷新恢复与掉线托管而不代替参赛者决策。
- 在轮次结束后收集三席复盘，推进下一局。
- 最后一局后触发评估 Agent，调用排名聚合器并生成比赛报告。

固定赛制优先使用确定性的主持程序。只有需要自然语言协调、动态选择实验、解释异常或生成报告时，才在其上增加主持 Agent。主持 Agent 不能访问或修改参赛 Agent 的私有手牌，不能提交参赛动作，也不能更改已开始比赛的模型、推理强度或策略快照。

## 推荐流程

```text
主持程序/主持 Agent
  -> 创建比赛与邀请
  -> 三个参赛 Agent 加入并锁定配置
  -> 游戏服务裁判执行多轮比赛
  -> 各席位提交局内复盘与比赛总结
  -> 评估 Agent 分析回放
  -> 排名聚合器生成事实指标与对比结果
  -> 主持层发布最终报告
```

## 后续实现顺序

1. 为回放汇总补齐超时率、拒绝动作率、决策耗时分位数和身份分组统计。
2. 增加同牌、同席、单变量实验批次模型。
3. 定义评估 Agent 的 JSON 输出 schema 与证据引用格式。
4. 实现确定性主持程序，再按需要接入主持 Agent。
5. 最后建立带运行环境证明的公开排行榜。
